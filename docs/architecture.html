What is Agent Land?

Agent Land is a session engine that runs long-lived coding agents in Docker containers on your server. Its mission: easy-to-deploy infrastructure for multi-agent workflows. Agent sessions can spawn sub-agents, watch their event streams, and compose them into larger pipelines — all through the platform's own API. The platform itself is five base components, three substrate services, and one fixed engine opinion (pi).

core Session — agent lifecycle, container, policy
core Connector — named sealed env bag
core Provider — LLM backend config
core Mount — named durable folder roadmap
core Event Stream — sequenced SSE log
core Platform Connector — self-injected API auth roadmap
substrate Docker — containers + volumes
substrate SOPS/Age — secrets at rest
substrate Flat JSON — persistence

Deployment

Production — Dokku on a VPS

One git push deploys the whole platform. Dokku auto-detects the root Dockerfile, builds it, provisions SSL, and places nginx with basic auth in front. No orchestration, no registry, no YAML — just git.

# One-time host setup (manual, documented in learnings)
dokku apps:create agent-land
dokku docker-options:add agent-land deploy \
  "-v /var/run/docker.sock:/var/run/docker.sock"
dokku http-auth:enable agent-land

# Deploy — every push to main
git push dokku main:master
Deploy workflow: .github/workflows/deploy.yml
Local dev — docker compose

Single-service compose file. The orchestrator mounts the Docker socket, secrets/, and data/. No auth, no SSL — just localhost:3000.

cp .env.example .env
docker compose up --build -d
curl http://localhost:3000/api/sessions

Base components — explained

core Session

The agent process itself — one pi --mode rpc agent in one Docker container. It is the atom of the platform; everything else exists to serve it.

  • Lifecycle: idle → running → waiting_for_input → back; stopped is terminal
  • Permission policy: auto (unattended) or manual (dialogs routed to a human)
  • Durable: survives orchestrator restarts; recover() re-attaches live containers
  • Fixed at creation: model, provider, connectors, mounts — never reconfigured live
Operations: create · prompt · respond · abort · kill · remove
core Connector

A named, sealed envelope of credentials — the WHO axis. Literal KEY: value pairs encrypted with SOPS/Age; injected as environment variables at session launch.

  • No type enum — fully generic. The platform never synthesizes variables.
  • Keys are public (listed, never exposed); values are sealed (decrypted in-memory, only at launch)
  • Field schemas, validation, and skills live outside — in connector packs
Shape: { name, url?, envKeys: [KEY], secretFile } — keys public, values never exposed over the API
core Provider

An LLM backend definition — the BRAIN axis. One generic record shape: id, baseUrl, api (dialect), models, defaultModel, and a sealed credential payload.

  • No vendor catalog in-core — preset values live in the CLI/packs
  • OAuth device flows (Copilot) run client-side; the server only stores the resulting tokens
  • Model resolution: explicit session model → provider default → platform default
Kinds: key-based or oauth token payload — same generic record
core Mount roadmap

A named, durable folder attached to a session container — the MATTER axis. Realized as a Docker volume with a label; outlives any session.

  • Attach at creation: mounts: {"/workspace": "proj-x"} — M:N
  • Exclusive live attach: at most one running session per mount; conflict returns the holder's session id
  • Carries: repo checkouts, warm node_modules, skill files, tooling dirs — the platform is content-agnostic
  • No mounts → auto-ephemeral per-session volume, removed on delete
Roadmap: fork (volume copy for parallel tracks)
core Event Stream

A session's sequenced, append-only record — the OBSERVATION + COMPOSITION channel. Broadcast live over SSE, persisted as the event log. Nothing else leaves the session.

Event vocabulary (agent-mechanical, never business-semantic):
  • status — lifecycle change
  • turn_start / turn_end
  • message_delta / message_end (errors ride here)
  • tool_start / tool_update / tool_end
  • agent_settled — idle, final answer ready
  • waiting_for_input / input_received — dialogs
Four consumer roles:
  1. Rendering — CLI terminal, API consumers
  2. Settle detection — al run, al watch
  3. Machine consumption — extract final answer, detect errors
  4. Cross-session observation — any client may read any session's stream
Properties: sequenced (dedupe), replayable (history + live in one stream), capped (10k in-memory), durable until session removal
core Platform Connector roadmap

Every session is a first-class client of the platform. At creation, the engine self-injects two env vars: AGENT_LAND_URL and AGENT_LAND_BASIC_AUTH. The agent can then curl the API to create child sessions, prompt them, and watch their event streams — the foundation of multi-agent orchestration.

What it unlocks:
  • An agent spawns sub-agents (planner → coder → reviewer)
  • An agent watches another session's event stream and reacts
  • No new platform features needed — the API is the composition surface
How it works: 
# Inside the agent container — reach back to the platform
curl -u "$AGENT_LAND_BASIC_AUTH" \
  "$AGENT_LAND_URL/api/sessions"
Injected at session creation alongside connector env vars. The agent holds the same auth as the user who launched it.

How to use — a concrete walkthrough

roadmap These walkthroughs show the target usage with durable mounts. Today sessions launch without mounts — each gets an ephemeral workspace volume that is removed with the session. Until mounts ship, run the same commands without --mount and let the agent clone fresh.

1. Define a project

A project is simply a named mount + a recipe of which connectors & provider to use. The mount is the durable footprint.

# First session: clone the repo into the project mount
al new --mount proj-agent-land:/workspace \
      --connectors "GitHub Personal All Repos" \
      --model deepseek-v4-pro

# The agent clones the repo into /workspace (the mount).
# Subsequent sessions skip the clone — state is warm.

# Second session: instant warm start
al new --mount proj-agent-land:/workspace \
      --connectors "GitHub Personal All Repos" \
      --model deepseek-v4-pro

2. One-shot task

al run "Extract formatAge into lib/format.ts and add tests" \
      --mount proj-agent-land:/workspace \
      --connectors "GitHub Personal All Repos" \
      --model deepseek-v4-pro \
      --verbose

3. Long-lived sidekick session

# Create and attach interactively
al new --mount proj-agent-land:/workspace \
      --connectors "GitHub Personal All Repos" \
      --model deepseek-v4-pro
# > chat prompt appears — type tasks, /quit to detach

# Re-attach later from anywhere
al chat <session-id>

4. Observe the event stream

# Watch until settled
al watch <session-id>

# Replay the full history
al log <session-id>

# Replay as raw JSON (for automation)
al log <session-id> --json

5. Compose a workflow (automation)

# Shell script that creates, prompts, waits, and reacts
SESSION=$(curl -s -u "$AUTH" -X POST "$URL/api/sessions" \
  -H 'content-type: application/json' \
  -d '{"model":"deepseek-v4-pro","connectors":["GitHub"]}' | jq -r .session.id)
curl -s -u "$AUTH" -X POST "$URL/api/sessions/$SESSION/prompt" \
  -H 'content-type: application/json' \
  -d '{"message":"Implement the feature from the spec in /workspace/spec.md"}'
al watch "$SESSION"                            # block until settled
PR=$(al log "$SESSION" | grep -oE 'pull/[0-9]+' | tail -1)
echo "PR opened: $PR"

Platform Connector — how agents reach back to the API

roadmap Self-injection is designed but not yet implemented — sessions do not yet receive AGENT_LAND_URL/AGENT_LAND_BASIC_AUTH automatically. Until it ships, child-session composition works by passing credentials explicitly (connector env or prompt).

For an agent session to spawn sub-agents and watch their results, it needs to reach the Agent Land API. The platform will self-inject its own URL and credentials at session creation — the agent becomes a first-class citizen of the platform.

What gets injected

Every session receives two env vars automatically:

  • AGENT_LAND_URL — the API base URL (e.g. https://agent-land.host.impromat.app)
  • AGENT_LAND_BASIC_AUTH — the same user:password that protects the API

The agent is now a client of the platform that hosts it.

What the agent can do with it
# Create a child session
curl -s -u "$AGENT_LAND_BASIC_AUTH" \
  -X POST "$AGENT_LAND_URL/api/sessions" \
  -H 'content-type: application/json' \
  -d '{"model":"deepseek-v4-pro","connectors":["GitHub"]}'

# Prompt it
curl -s -u "$AGENT_LAND_BASIC_AUTH" \
  -X POST "$AGENT_LAND_URL/api/sessions/CHILD_ID/prompt" \
  -H 'content-type: application/json' \
  -d '{"message":"Research the login flow and write a spec"}'

# Watch its event stream for the result
curl -s -u "$AGENT_LAND_BASIC_AUTH" \
  "$AGENT_LAND_URL/api/sessions/CHILD_ID/events"
Or use the al CLI inside the container if it's mounted.

Step by step
  1. You attach: al chat <session> — interactive, from anywhere
  2. You ask: "Plan and implement the login rate-limiting feature"
  3. Agent spawns a planner: creates a child session, prompts it with the task, watches its SSE stream for the final answer
  4. Agent reads the plan: extracts the spec from the child's event stream
  5. Agent spawns a coder: creates another child session with the spec as the prompt, watches it to green PR
  6. Agent reports: "Done — PR #42 is green. Here's the plan and the diff."
Why this is the platform's "hello world"
  • It exercises every base component: Session, Connector, Provider, Mount, Event Stream
  • It proves the composition loop: Session → Event Stream → (agent) → new Session
  • It needs zero new platform features — just the API that already exists + the self-injected auth
  • It's the seed of every larger pattern: workflows, scheduled tasks, multi-agent review, gated deploys

The next step after the hello world: the agent itself watches child sessions and reacts — on red CI, it re-prompts the coder; on green, it opens a review session. That's the orchestration loop, built entirely from the base components and the API.

Where Agent Land is different

No workflow engine in the core

LangChain, CrewAI, and Dify all ship a workflow/routing/graph engine inside the platform. Agent Land has none — the composition loop (Session → Event Stream → new Session) is the only primitive. Workflows are recipes (prompts, scripts, YAML) that the agent interprets, not the platform.

Git-push deploy, not k8s

Every other self-hosted platform requires Docker Compose at minimum, typically k8s or a cloud VM with a complex setup. Agent Land is a single Dockerfile — Dokku builds it, provisions SSL, and places nginx in front. One git push.

Sessions are atoms, not invocations

LangGraph sees the world as a graph of function invocations. Agent Land sees the world as sessions — long-lived agent processes that survive restarts, can be re-attached from anywhere, and spawn child sessions. A session keeps its context across turns; a graph node is stateless.

No vendor knowledge in the platform

Connectors are literal sealed env bags — no type enum, no field schemas, no typed integrations. Providers are generic records — no catalog, no device-flow machinery in-core. LangChain's integration catalog, Dify's connector nodes, and CrewAI's typed tools all bake vendor knowledge into the platform. Agent Land pushes it out to packs and presets.

SOPS/Age, not env vars

Every other tool stores secrets as plain environment variables or cloud secrets. Agent Land encrypts them at rest with SOPS/Age — decrypted in-memory, only at agent launch, only for the connectors and providers that session selected. The decrypted values never touch disk.

JSON/SSE API, no SDK

LangChain, CrewAI, and Dify each have their own SDK. Agent Land has a JSON/SSE API — the al CLI is a thin client, and any language can drive it. The platform connector (self-injected auth) means agents themselves are API clients — no SDK needed inside the agent either.

Design invariants

  1. Registries are independent and outlive sessions. Connectors, Providers, and Mounts are catalogs; sessions are transient compositions.
  2. Create-time is resolution-time. Env, engine config, and mount binds are fixed when the session starts. Changing a connector affects the next session.
  3. The platform observes, never interprets. Everything it knows about agent behavior comes from the event stream — the vocabulary is agent-mechanical, never business-semantic.
  4. No technology baked into containers. The agent image is node + pi + git + curl. Skills, tooling, dependency caches — everything else is a mount or a pack, owned by the use case.
  5. Every session is a platform client. The engine self-injects AGENT_LAND_URL + AGENT_LAND_BASIC_AUTH at creation (roadmap). Any agent can spawn sub-agents and watch their event streams — multi-agent composition needs no new primitives.
  6. Everything above is composition. Projects, workflows, schedules, gates — built from the base components, never inside them.
