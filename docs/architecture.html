The idea

Agent Land runs long-lived coding agents in Docker containers on your server. The engine does one thing well: launch a session with three injected capabilities (connector, provider, mount) and stream its behavior as a single, sequenced event log.

The platform observes and reports — vendor, workflow, and domain knowledge all live in the use-case layer. The CLI (al) is the primary interface; the JSON/SSE API is the composition surface. Projects, workflows, schedules — recipes built from the primitives.

The six primitives

PrimitiveWhat it isStatus
Connector Named sealed env bag. Credentials encrypted at rest (SOPS/Age), decrypted in-memory only at launch. The API exposes env var names only — values never leave the server. implemented
Provider Generic LLM backend record: id, baseUrl, api (dialect), models, defaultModel, sealed credentials. No vendor catalog in-core. implemented
Mount Named durable Docker volume attached to sessions — repo checkouts, warm caches, skill files. M:N attach, at most one live session per mount. roadmap
Session One pi --mode rpc agent in one limited Docker container. Lifecycle idle → running → waiting_for_input → back; stopped is terminal. Permission policy auto or manual. Survives orchestrator restarts. implemented
Event Stream Sequenced, append-only record — broadcast live over SSE, persisted per session. The only observation channel: CLI rendering, settle detection, scripts, and other agents. implemented
Platform Connector At session creation the engine injects its own API URL + auth, so an agent can create child sessions, prompt them, and watch their streams. roadmap

A workflow is just a script that creates sessions, prompts them, watches their event streams, and reacts. roadmap Agent-driven looping (agents spawning agents) arrives with the Platform Connector; today the loop is driven externally via the CLI and the API.

Hello world — how to use

Three commands take you from zero to a running agent:

1. Register a connector

Credentials are encrypted at rest (SOPS/Age) and never leave the server — the API only ever shows their names.

al connectors add --name github --url https://api.github.com \
    --field GITHUB_TOKEN=ghp-xxx

2. Run a one-shot session

Create, prompt, stream to settle, print the final answer, and clean up:

al run "Clone the repo and fix the typo in README" \
    --model deepseek-v4-pro --connectors github --rm

3. Chat interactively — re-attachable from anywhere

al new --connectors github     # create + enter the chat overlay
/quit                          # detach — session keeps running
al chat <session-id>           # re-attach later, from any machine

The API is the composition surface — any language, any script, even the agents themselves:

SESSION=$(curl -s -u "$AUTH" -X POST "$URL/api/sessions" \
  -H 'content-type: application/json' \
  -d '{"model":"deepseek-v4-pro","connectors":["github"]}' | jq -r .session.id)
al watch "$SESSION"        # block until settled

Design invariants

  1. Registries outlive sessions. Connectors, providers, mounts are catalogs; sessions reference but never mutate them.
  2. Create-time is resolution-time. Env, engine config, and mounts are fixed when the session starts.
  3. The platform observes. The event stream is the only observation channel; its vocabulary is agent-mechanical.
  4. Vendor knowledge and workflows stay in the composition layer. Presets, packs, projects, workflows — recipes that build on the primitives.
