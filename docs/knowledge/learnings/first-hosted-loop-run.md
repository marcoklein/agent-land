# First hosted loop run (curl scheduler)

On 2026-09-20 the external loop[^loop] — bash + curl + jq on the bare host, driven by a 5-minute cron[^deploy] — drove [alt-g1f1][^ticket] through the full automatic ladder with no human between claim and gate: `needs-refinement → needs-questions → needs-research → needs-design`, each phase a spawned session, then parked at the design gate and opened [PR #155][^design-pr].

## What worked

- One phase per tick: claim → spawn session → poll `status` → re-derive `STATUS:` from `work/<id>/thoughts.md` → retag → push.
- The design phase opened a real agent-land PR and parked the ticket at `human`; the next tick correctly skipped it (`loop: ticket alt-g1f1 parked at human gate`).

## Bugs surfaced (and fixed)

1. **Env vars were not exported.** `server/05-ticket-loop.sh` wrote `VAR=value` lines; cron sources them in `/bin/sh`, so they stay shell-local and `scripts/loop.sh` (child bash) never sees them. The loop silently fell back to `AGENT_LAND_URL=http://localhost:3000` with no auth, so connector discovery returned empty — `loop: no GitHub connector found`. Fixed by prefixing `export` on every line.

2. **`set -e` + command-substitution assignment crashes.** `current_phase=$(get_current_phase "$id")` exits the whole script when `get_current_phase` returns non-zero — i.e. any ticket with `loop` but no ladder phase tag (a `human`-parked ticket). The `if [[ -z … ]]` guard below it was dead code. Fixed by checking `has_human_tag` first and adding `|| true`.

3. **Board mount was stale.** The web UI reads a static `board.json` (regenerated by the loop on every push) via a Dokku storage mount; the mount still pointed at the old checkout `/var/lib/agent-land-tickets` instead of `/srv/agent-land-tickets`, so the board showed yesterday's data. Fixed by repointing the mount.

## Lesson

The connector-discovery path had only ever been exercised manually, never under the cron it actually runs as — so the export bug survived until the first real ticket. "It works when I run it by hand" is not a deployment check when the real driver is cron: verify under the same shell and environment that will run it.
